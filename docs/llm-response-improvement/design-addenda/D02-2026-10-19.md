# D02 design addendum — separate structured output bounds

Date: 2026-10-19 Asia/Kolkata. This addendum is required by the reproduced adapter defect before implementation.

## Decision

The user selected the recommended numeric limits after reviewing the reproduced defect: **2,048 generation tokens** and **16,384 serialized JSON characters**. Keep the existing `ConversationPolicy.output_char_limit` as the final dialogue Unicode code-point ceiling (maximum 600). Add two independent settings for the durable structured-generation adapter:

- `conversation_contract_json_char_limit`: serialized provider JSON response characters, integer 1–65,536.
- `conversation_generation_token_limit`: provider generation tokens, integer 1–16,384.

These settings default to the selected bounded values: `conversation_generation_token_limit=2048` and `conversation_contract_json_char_limit=16384`. They can be overridden within their validation bounds. They do not opt the application into the durable runtime; the remaining runtime policy still must be explicitly complete, and `conversation_enabled` remains false by default. This makes the D02 limit choice concrete without changing deployment routing or enabling durable generation.

## Runtime semantics

- The adapter prompt continues to receive the dialogue code-point ceiling.
- OpenAI-compatible `max_tokens` uses only `conversation_generation_token_limit`.
- The returned serialized content is measured in Python Unicode code points and checked against `conversation_contract_json_char_limit` before JSON parsing.
- Existing composition, response validation, and finalization retain the final assembled-dialogue ceiling. Metadata capacity does not relax final dialogue validation.
- Deadlines, turn-wide call/repair allowances, schema validation, consent, receipts, idempotency, scope, and fallback policy remain unchanged.
- Structured adapter diagnostics advance to contract version 2. Legacy `/chat` execution and the historical dialogue-only runner are unaffected.

## Compatibility and migration

The durable runtime configuration remains all-or-nothing. The new bounded fields are available even in legacy-only settings but do not count as an explicit durable policy; deployments with all prior policy fields unset continue legacy-only startup. Deployments that configure a durable policy inherit the selected limits unless they override them. The currently inspected local configuration has all other durable policy fields unset and `conversation_enabled=false`, so this change does not activate or re-route current traffic. No schema/data migration is required.

## Evidence

`docs/evidence/llm-response-improvement/reproduce_budget.py` returns a valid `TurnProposal` fixture whose reply text is 11 code points and whose JSON is 917 characters. Under the old code, `response_budget=600` was sent as `max_tokens=600` and the valid typed output was rejected as `GenerationMalformed`. Focused tests assert acceptance under the selected limits and rejection above the serialized JSON ceiling.

## Rollback

Rollback the adapter/settings change together. The selected settings do not opt into durable runtime. Keep durable generation disabled until its full policy and adoption gates are verified. Receipts and persisted turn identity are outside this change and must remain intact during rollback.
